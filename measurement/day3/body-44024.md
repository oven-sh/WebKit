### Problem
- The interpreter of JavaScriptCore (LLInt) caches one object shape for each property read. A read that sees several shapes calls `llint_slow_path_get_by_id` each time: about 1.28 M calls in a session of a large application.
- The object of a `vm.constants.DONT_CONTEXTIFY` context returns `undefined` from JIT code for a property that the context got later. `NodeVMSpecialSandbox` (`src/jsc/bindings/NodeVM.h:103`) has no flag against a cache of "no such property".

### Fix
- Pin WebKit to the preview build of oven-sh/WebKit#735, `autobuild-preview-pr-735-867429ea`: the current pin (`f20ce77445`) plus that change. Before this merges, replace the tag with the merge commit.
- New JSC options. On: `missCountForLLIntTierUp` (12), `useLLIntStringLengthFastPath`. Off: `useLLIntUnsetCaching`, `useLLIntPrototypeCacheRearming`, `useStartupJITDeferralAfterLLIntMisses`. `BUN_JSC_<option>` sets one.
- `NodeVMSpecialSandbox` gets `GetOwnPropertySlotIsImpureForPropertyAbsence`.
- Verified: `test/js/bun/jsc/llint-get-by-id-caches.test.ts` (new), `test/js/node/vm/vm.test.ts` (one new test), `test/js/bun/compile/jit-policy.test.ts`.

### Background
- The LLInt runs a function until its execution counter reaches a threshold. Then the Baseline JIT compiles it, with a cache entry for each shape.
- `--compile-jit-policy` multiplies that threshold at startup. A function that the miss count sends to the Baseline JIT does not wait for it.
- oven-sh/WebKit#735 has the design and its alternatives.

### Downsides
- A small `tsc` run in `jsc` at a JIT policy of 10 has 423 more compiles. They run 4.3% more instructions and make 2.1 MB more JIT code. The rest of the main thread runs 5.3% fewer instructions.
- A read of a missing `globalThis.x` stays `undefined` in the JIT after a later script declares `var x` (Bun 1.4.3 has that). It shows sooner in a function that tiers up early for the misses of another read.

**To compare in one binary.** `BUN_JSC_missCountForLLIntTierUp=0 BUN_JSC_useLLIntStringLengthFastPath=0` is the behaviour before the change. `BUN_JSC_useLLIntUnsetCaching=1 BUN_JSC_useLLIntPrototypeCacheRearming=1` turns the other two on. `BUN_JSC_useStartupJITDeferralAfterLLIntMisses=1` makes the JIT policy apply to the functions that the misses send to the Baseline JIT.

**The context object.** `NodeVMSpecialSandbox::getOwnPropertySlot` answers with what the global object of the context has. `NodeVMGlobalObject::put` stores a symbol that is assigned to a name with no declaration on the global object itself. So the context object gets a property and keeps its structure, and an inline cache that holds "no such property" for that structure stays valid. The flag tells the caches of JavaScriptCore not to hold that for the class. The new test in `vm.test.ts` reads a property of the context object 5000 times, assigns it in the context, and reads again. Bun 1.4.3 fails it, and so does a debug build of this branch without the flag: the read in JIT code returns `undefined`, and `ctx.laterSymbol` returns the symbol. Bun has three more classes with their own `getOwnPropertySlot` (`NodeVMGlobalObject`, `JSNodeSqliteLimits`, `JSSharedEnvMap`). Each has `ProhibitsPropertyCaching`.

**The test.** `llint-get-by-id-caches-fixture.js` warms a property read up, changes what the read must return, and reads again: a property that appears on the receiver, on its prototype, on `Object.prototype`, as a getter, through a new prototype, through a proxy, on a primitive, on `process.env`, on the object of a `node:vm` context, and the length of strings. The test runs it in 12 configurations of the options, with and without the JIT. With the release that is current, 10 of the 12 configurations fail, because the options do not exist there. Without the flag of `NodeVMSpecialSandbox`, the 6 configurations with the JIT fail.

**The global variable block of the fixture.** A `var` of a later script (`vm.runInThisContext`) is a property of the global object, and the global object keeps its structure. An inline cache of the JIT keeps "no such property" for it, and returns `undefined` after the declaration. That is so without this change: with `BUN_JSC_thresholdForJITAfterWarmUp=10 BUN_JSC_useConcurrentJIT=0`, Bun 1.4.3 fails that block. A read that finds no property does not count as a miss if the receiver is the global object or has it on its prototype chain. So the 20 reads of the block do not send the function to the JIT, and the block runs in each configuration.

**Docs.** `docs/bundler/executables.mdx` says that the JIT policy does not apply to a function whose property read or write misses the cache of the interpreter 12 times.

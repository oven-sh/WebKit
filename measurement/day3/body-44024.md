### Problem
- The interpreter of JavaScriptCore (LLInt) caches one object shape for each property read. A read that sees several shapes calls `llint_slow_path_get_by_id` each time: about 1.28 M calls in a session of a large application.
- The object of a `vm.constants.DONT_CONTEXTIFY` context returns a stale result after the context got a property. `NodeVMSpecialSandbox` (`src/jsc/bindings/NodeVM.h:103`) has no flag against inline caches.

### Fix
- Pin WebKit to the preview build of oven-sh/WebKit#735, `autobuild-preview-pr-735-7da0e718`: the current pin (`f20ce77445`) plus that change. Before this merges, replace the tag with the merge commit.
- New JSC options. On: `missCountForLLIntTierUp` (12), `maximumBytecodeCostForLLIntMissTierUp` (10000), `useStartupJITDeferralAfterLLIntMisses`, `useLLIntStringLengthFastPath`. Off: `useLLIntUnsetCaching`, `useLLIntPrototypeCacheRearming`. `BUN_JSC_<option>` sets one.
- `NodeVMSpecialSandbox` gets `ProhibitsPropertyCaching`, which `NodeVMGlobalObject` has.
- Verified: `test/js/bun/jsc/llint-get-by-id-caches.test.ts` (new), `test/js/node/vm/vm.test.ts` (two new tests), `test/js/bun/compile/jit-policy.test.ts`.

### Background
- The LLInt runs a function until its execution counter reaches a threshold. Then the Baseline JIT compiles it, with a cache entry for each shape.
- `--compile-jit-policy` multiplies that threshold at startup. It also multiplies the lower threshold of a function whose property access keeps missing.
- oven-sh/WebKit#735 has the design and its alternatives.

### Downsides
- A small `tsc` run at a JIT policy of 10 has 282 more compiles and 4.0 MiB more memory at its end. The main thread runs 4.6% fewer instructions outside the compilers.
- A read of a missing `globalThis.x` stays `undefined` in the JIT after a script declares `var x` (Bun 1.4.3 has that, oven-sh/bun#44097 fixes it). It shows sooner in a function that tiers up early.
- A property read of the object of a `DONT_CONTEXTIFY` context has no inline cache.

**Measurements.** They are in the Notes of oven-sh/WebKit#735, for the TypeScript compiler and React server rendering in the `jsc` shell. With a startup deferral scale of 10, the TypeScript compiler on 40 files makes 109723 calls of the three slow paths of the interpreter where it made 370949, with 2778 Baseline compiles against 2536. On 4 files the main thread runs 3.591 G instructions outside the compilers and the collector where it ran 3.764 G (-4.6%), and the compilers run 4.089 G against 3.974 G (+2.9%). With no scale the gain is 0.3%, for 1.9% more in the compilers. In Bun itself, one thing was measured: the start of a bundle of six packages at a JIT policy of 10 has 10 Baseline compiles and 24000 bytes of Baseline code, with and without the change.

**To compare in one binary.** `BUN_JSC_missCountForLLIntTierUp=0 BUN_JSC_useLLIntStringLengthFastPath=0` is the behaviour before the change. `BUN_JSC_useStartupJITDeferralAfterLLIntMisses=0` takes a function out of the JIT policy after the misses. `BUN_JSC_maximumBytecodeCostForLLIntMissTierUp=0` takes the limit of the size away. `BUN_JSC_useLLIntUnsetCaching=1 BUN_JSC_useLLIntPrototypeCacheRearming=1` turns the two caches on.

**The context object.** `NodeVMSpecialSandbox::getOwnPropertySlot` answers with what the global object of the context has. `NodeVMGlobalObject::put` stores a symbol that is assigned to a name with no declaration on the global object itself, and a `var` of a script is a variable of the global object. So the context object gets a property and keeps its structure, and an inline cache for that structure stays valid: one that holds "no such property", or one that holds the value of the prototype. `ProhibitsPropertyCaching` tells JavaScriptCore to make no inline cache for the class, as for `NodeVMGlobalObject`. The two new tests in `vm.test.ts` read a property of the context object, make the context get it, and read again. Bun 1.4.3 fails both, and so does a debug build of this branch without the flag. Bun has three more classes with their own `getOwnPropertySlot` (`NodeVMGlobalObject`, `JSNodeSqliteLimits`, `JSSharedEnvMap`). Each has `ProhibitsPropertyCaching`.

**The test.** `llint-get-by-id-caches-fixture.js` warms a property read up, changes what the read must return, and reads again: a property that appears on the receiver, on its prototype, on `Object.prototype`, as a getter, through a new prototype, through a proxy, on a primitive, on `process.env`, on the object of a `node:vm` context, and the length of strings. The test runs it in 13 configurations of the options, with and without the JIT. With the release that is current, each of the 13 configurations fails: 11 because the options do not exist there, and 2 for the stale read of the context object. Without the flag of `NodeVMSpecialSandbox`, the blocks of the context object fail.

**The global variable block of the fixture.** A `var` of a later script (`vm.runInThisContext`) is a property of the global object, and the global object keeps its structure. An inline cache of the JIT keeps "no such property" for it, and returns `undefined` after the declaration. That is so without this change: with `BUN_JSC_thresholdForJITAfterWarmUp=10 BUN_JSC_useConcurrentJIT=0`, Bun 1.4.3 fails that block. A read that finds no property does not count as a miss if the receiver is the global object or has it on its prototype chain. So the 20 reads of the block do not send the function to the JIT, and the block runs in each configuration.

**Docs.** `docs/bundler/executables.mdx`, and the JSDoc of `Bun.unsafe.setJITPolicy` and of `compile.jitPolicy` in `bun.d.ts`, say that the Baseline JIT compiles a function earlier than the scale says when one property access of it keeps taking the slow path of the interpreter.

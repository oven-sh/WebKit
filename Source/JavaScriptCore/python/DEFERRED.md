# Deferred, undecided, and different on purpose

The list the project keeps of what Python in JSC does not do. Three kinds of entry: **different** (follows from the design, and
stays), **experiment** (needs trying out before it can be decided), **deferred** (known work, not started or not finished).

## Different: follows from the design

| What                                         | Why, and what happens instead                                                                                                                                                                                                    |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Objects are not freed at the last `del`      | There are no reference counts. Finalizers and weak reference callbacks run at the first safe point after the collection that finds the object dead; `gc.collect()` forces it; everything left is finalized at exit. See README.   |
| Buffered output reaches files earlier        | `open(path, "w").write(text)` counts on the file being closed when it is dropped. Here the streams over files that hold output are kept in a list, and are written out before the program, or anything it starts, can look at a file or do to a file or a descriptor what would come out differently afterwards: `open`, the `stat` family and `DirEntry.stat`, reading, writing, seeking, truncating and closing through `os` or a `FileIO`, `dup2`, `utime`, `rename`, `link`, starting a process, `gc.collect()`, a call of the host. So `f.write("abc"); os.stat(path).st_size` is 3, not 0. Only streams that are exactly what `open()` makes (`TextIOWrapper`, `BufferedWriter`, `BufferedRandom` over a `FileIO`, none of a derived class, whose `write` and `flush` would be seen to run), and not `sys.stdout` and `sys.stderr`. What tells another process by other means that a file is ready (a socket, a signal) does not write them out. The descriptor itself stays open until a collection finds the file: the reader of a pipe whose writer was dropped gets the data, but no end of file until then. |
| `sys.getrefcount`                            | There are no counts: it returns a constant. |
| `gc.collect()`'s result                      | Real: how many objects it found that reference counts would not have freed (README). Not always CPython's number: the first call also finds what has piled up since the program started; a class counts for as many objects as it is made of here; an object with a finalizer that hangs off a cycle without being in one is not counted; what is written in Python here and in C there (`functools.lru_cache`) has cycles of its own; beyond four million dead cells nothing is counted. `uncollectable` is always 0, `candidates` counts cells. |
| `gc.disable()`, thresholds, generations, `freeze()` | The engine collects when it sees fit, by the bytes allocated, not by the number of objects (an allocation count like CPython's 2000 would cost 130 to 200 us for every 50 us of allocating). `disable()` only stops `gc.callbacks` and `get_stats()` from being told of the engine's own collections: finalizers of cyclic garbage may still run. `set_threshold()` is remembered, `get_count()` is `(0, 0, 0)`, `get_objects(generation=0 or 1)` is empty and `2` has everything, `freeze()` does nothing and `get_freeze_count()` is 0. |
| `gc.callbacks` for the engine's own collections | Called after the fact, at the next safe point: "start", what the collection found, "stop". `collected` is 0: only a collection that was asked for counts. |
| What `gc` does not hand out                  | The namespace of a class (`gc.get_referents(cls)` gives what is in it), the `__dict__` of an instance that has not asked for it, and whatever is a part of another object here. `get_referents()` leaves out attributes that are numbers. `get_objects()` and `get_referrers()` each cost a full collection that is listened to. |
| Finalizers and callbacks show up where they run | `sys.settrace`, `sys.setprofile`, `sys.monitoring`, `pdb` and `cProfile` see the code of a `__del__` or of the callback of a weak reference like any other code, as in CPython, but at the safe point after the collection, not where the object was dropped: a debugger that steps may find itself in `importlib._bootstrap`'s `cb`. A signal that comes while one runs is handled in its frame, as in CPython. |
| A weak reference that dies with its referent | Its callback is not called. In CPython it is, if the referent's count falls to zero first: `self.ref = weakref.ref(self, callback)` without a cycle. |
| Order of finalizers in the engine's own collections | As with reference counts where one object with a finalizer reaches another. Siblings (the items of a dropped list) go in the order they were made, not in CPython's, and a cycle of objects without finalizers above them is not seen: only a collection that was asked for looks at all that died. Objects that were dropped one after the other and are found by the same collection go in the order they were made. |
| `__del__` given to a class after instances exist | The instances there are then are found and will be finalized. Among them are those that were dropped before and that no collection has found yet: an object dies when a collection finds it.                                  |
| All NaNs are one object                      | A NaN is an immediate value: `float('nan') is float('nan')`, so `x in [x]`-style identity shortcuts see any NaN as the same. The sign and payload of a NaN are not kept.                                                          |
| `id()` of numbers, `is` on numbers and strs  | Numbers are immediates: equal ints and floats are identical. Equal strs need not be.                                                                                                                                             |
| A whole `float` becomes a number in JS       | `2.0` handed to JS is `2`, and comes back as the int `2`. Inside a list JS can see the cell that holds it.                                                                                                                        |
| An int beyond 2^53 is a BigInt in JS         | And a BigInt from JS is an int in Python.                                                                                                                                                                                         |
| `None` is `undefined` in JS                  | And both `undefined` and `null` are `None` in Python. So `JSON.stringify({"a": None})`, given a dict, leaves `a` out, as it does for any property that is `undefined` (in a list it is `null`); `json.dumps` writes `null`. |
| `bytecode`: `co_code`, `dis`, `.pyc`         | The bytecode is JSC's. `co_code` is made up: bytes that differ for code that differs (libraries compare them to tell functions apart), ending in `LOAD_GLOBAL`, `LOAD_ATTR`, `STORE_*` and `IMPORT_NAME` units for the names the code uses and the modules it imports, which is what `inspect.getclosurevars`, cloudpickle and `modulefinder` look for; `dis` shows that and no more. `co_linetable` is the marshalled code, from which `types.CodeType(...)` and `code.replace()` make code again. `replace()` changes what describes the code (names, file, first line, flags) and, in `co_consts`, a number, a str or a bytes for another of its type and the code of a function for code with as many free variables; anything else that the instructions depend on is a `NotImplementedError`. Code with the code of a function replaced cannot be marshalled. A `.pyc` file, and what `marshal` writes for a code object, is read by the build of Bun that wrote it and by nothing else, and CPython's are not read here. What it writes for other values is read by CPython and the other way round, but is not the same bytes from version 3 on: which objects CPython numbers for reference depends on reference counts. |
| Comparisons in JS are true or false          | `a < b` in JS is the truth of what `__lt__` returns.                                                                                                                                                                              |
| JS has no `//`, `@`, `+=` of its own         | `a += b` in JS is `a = a + b` (`__add__`, not `__iadd__`). Floor division and matrix multiplication are method calls.                                                                                                             |

## Experiments

| What                              | The question                                                                                                                                                                                                                                       |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Whole floats as heap numbers      | Teach JSC a non-object "heap number" cell that `typeof`, `===`, `Map` keys and the JITs treat as a number, so that a `PyFloat` inside a list is indistinguishable from a number in JS. Every place that enumerates the primitive cell kinds is touched. |
| Lists of floats as double arrays  | A list that holds only floats could use JSC's `ArrayWithDouble`, marked by its Structure as "every element is a float": no cells, and JS sees plain numbers. An int stored by JS becomes a float.                                                    |
| dict as a JS object or Map        | `PyDict` is its own hash table (keys compare with `__eq__`/`__hash__`, insertion order, any hashable key). JS sees it as an exotic object. Whether it should also be a `Map` to JS is open.                                                          |
| Prompt finalization               | Today: an object with a finalizer that is dropped young is finalized at the next collection of the young generation (some 150,000 small allocations, 4 to 15 ms of allocating), or after 50 ms of waiting for anything; never while the program computes without allocating; and one that has come through a collection only at the next full collection, which does not come while the old generation does not grow. A collection of the young generation costs 95 to 210 us at best, so one per 2000 allocations (CPython's threshold) would make allocating code 3 to 5 times slower, and the engine's own trigger is already where such collections cost 4 %. Counted over CPython's tests and our benchmarks, objects with finalizers that die unclosed are few (under 1 % of the time at one collection each, 10 to 20 % in `test_io`, `test_zipfile`, `test_pathlib`), but those that are made are many (4 million in 9 s of asyncio), and nothing cheap says which of them has just been dropped. To try: (1) a collection at the points where a program says that it drops something, if the object is registered or weakly referenced: `del name`, `generator.close()`, the end of a `for` over an unfinished generator; under a budget of time. That is the idiom of most tests that still fail for this reason (`del a; assertNotIn(2, weak_dict)`). (2) a full collection now and then while old objects with finalizers exist (1 % of the time). (3) a timer that asks for a collection of the young generation a few ms after an object with a finalizer is made, for programs that do not allocate. Escape analysis for "freed when the function returns" has little to work with: any method call lets `self` escape. |
| JIT                               | Python runs in the LLInt, with fast paths and inline caches there (README, Code). No Baseline, DFG or FTL. The caches are monomorphic.                                                                                                              |
| Consumers of generators in C++    | `for`, `yield from` and `await` resume a generator without leaving the interpreter (README, Code). `sum`, `list`, `any`, `min`, `"".join`, `next()`, `send()` and the like are C++ and enter the VM anew for each item: about 1.3 times CPython's cost. They could be hidden functions in bytecode, which needs frames that tracebacks skip. asyncio's own tasks and futures are the pure Python ones (no `_asyncio`): 2.5 times CPython's cost per task switch. |
| Recursion limit                   | The frames of Python functions are on the machine stack, as those of JS are. With `sys.setrecursionlimit()` raised, recursion ends in `RecursionError` where the stack does: after 30,000 to 40,000 calls on a stack of 8 MB, where CPython, which keeps the frames of Python functions elsewhere, goes on to the limit that was set. `threading.stack_size(n)` gives a thread `n` bytes and the part that JSC keeps in reserve on top. |

## Deferred

| What                                      | State                                                                                                                                                                  |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Threads                                   | Done, with a GIL: see README. No free threading. Holes, worst first: `_sqlite3` never lets go of the GIL and SQLite has a mutex per connection, so two threads that share a connection can deadlock (one is switched out inside a user function, the other blocks on the mutex with the GIL), and `check_same_thread` is ignored; JS code never yields the GIL, so a long computation in JS starves the threads; a thread that reads into or writes from the memory of WebAssembly keeps the GIL in the system call (that memory cannot be pinned); what other threads leave to the main thread (dead objects of the host, a termination) waits while the main thread is in a long system call; a blocking call costs about 0.4 µs more while another thread exists; zlib, `_zstd` and hashlib keep the GIL while they work (`_bz2` and `_lzma` let go of it); no more than 4 global objects with Python in one VM; POSIX only, tested on Linux only. |
| `fork`, `multiprocessing`, subinterpreters| No `os.fork`, no subinterpreters. `multiprocessing` has the start method `spawn` and no other, as on Windows (Bun's `_bun_import.py` takes `fork` and `forkserver` out of `multiprocessing.context` when it is imported; `get_context("fork")` still gives a context, which starts no process): `Process`, `Pool`, `Queue`, `Manager`, locks, `ProcessPoolExecutor` work. `Value` and `Array` need `_ctypes`. `os.spawnv` and its kin, which `os.py` writes with `fork`, are functions of `posix` here. |
| Subprocesses                              | `_posixsubprocess.fork_exec` is complete but for `preexec_fn`, which raises `RuntimeError`: no code of the engine can run in a forked child.                              |
| Sockets                                   | Addresses of `AF_INET`, `AF_INET6`, `AF_UNIX`, `AF_NETLINK`; other families have their constants only. No `sendmsg_afalg`, no `CAPI`. Names that are not ASCII need `encodings.idna`. |
| `ssl`                                     | Done, on Bun's BoringSSL (`src/jsc/bindings/python/BunPythonSsl.cpp` in Bun), which is not OpenSSL. `ssl.OPENSSL_VERSION` is the library's own "OpenSSL 1.1.1 (compatible; BoringSSL)". Not there, and said so (`HAS_*` is False, `NotImplementedError`, or the library's refusal as `SSLError`): post-handshake authentication, external PSKs in TLS 1.3, choosing the cipher suites of TLS 1.3 (`set_ciphersuites`), the signature algorithm of one's own side (`client_sigalg()` on a client), security levels (`@SECLEVEL=n` in a cipher string is refused, `security_level` is 0), finite-field DH (`load_dh_params` reads the file and that is all), compression, kernel TLS, renegotiation. Options that the library has no use for are 0 (`OP_NO_COMPRESSION`, `OP_NO_SSLv3`, `OP_SINGLE_DH_USE`, ...). The reasons of errors have the library's names, and their texts are those names in lower case. `session_stats()` counts handshakes and hits itself; misses, timeouts and `cache_full` stay 0. `ticket_lifetime_hint` of a TLS 1.3 session is 0. A context has a certificate for each kind of key, as in OpenSSL, but what `set_server_sigalgs()` and `set_client_sigalgs()` say about one's own signatures binds only the one loaded last. Certificates, keys and CA files are read by the library from the real file system, not from the virtual directory in the executable. The library runs with the GIL held: only waiting for the socket lets other threads in. `set_default_verify_paths()` is `$SSL_CERT_FILE`, `$SSL_CERT_DIR` and the system's OpenSSL directory (`/etc/ssl`); where neither variable is set and that directory has no `cert.pem` and no hashed certificates, the roots that come with Bun. No Windows (`enum_certificates`). |
| `mmap`                                    | The memory is that of an `ArrayBuffer`, so at most 4 GiB in one mapping.                                                                                                  |
| C API (`abi3t`), extension modules        | Not started. `PyObject*` would be a handle on a `JSValue`. No numpy until then.                                                                                            |
| Package manager (`bun install` from PyPI) | Not started, by decision: the language first.                                                                                                                             |
| Event loop                                | Done, see README. Missing: `import asyncio` is needed for any coroutine that JS awaits, even one that never suspends, and is slow to import; `_asyncio` (`runtime/PyAsyncio.cpp`) says "exception was never retrieved" and "Task was destroyed but it is pending!" when the collector finds the object, not when the last reference goes, its types have no docstrings, `FutureIter` and `TaskStepMethWrapper` cannot be instantiated, and there is nothing for `_remote_debugging` to read (`python -m asyncio ps`); `time.sleep`, `os.read`, `waitpid` and lock waits block the thread without turning the host's loop; Windows. |
| Standard library in the binary            | A read-only virtual directory (`runtime/PyVirtualFiles.h`). It has no directory descriptors (`os.fwalk`, `dir_fd`), no `chdir`, and other programs cannot see it.          |
| Start-up and import speed                 | Compiled code is cached (README, Imports). What is left of start-up is making the built-in types and running `importlib`, `site` and what they import. Not done: the code of the standard library could be made when Bun is built and be part of the executable, so that there is no first run; directories of builds that are gone stay in the user's cache directory; a function that is defined decodes all of its `CodeInfo`, names of variables included, though most of it is only needed by introspection. |
| Python importing JS                       | Done, see README. Missing: `import a.b` for a subpath of a JS package (use `importlib.import_module("a/b")`), modules with top-level await (`require()` refuses them), the name of the module in `ImportError` messages. |
| JS importing the standard library          | Done: `import json from "python:json"`, see README ("Imports", "From JavaScript"). Tests of the standard library translated from CPython's into TS are in Bun, `test/js/bun/python/stdlib/`: a first 15 files, whose README is the guide to writing Python in JS. Most of `Lib/test` is not translated. Types are `any`. |
| What JS cannot say to Python               | Found by those tests. Done since: `with()` and `asyncWith()` in `bun:python`, `class extends`, functions of JS as methods, tasks of promises. Left: `using` (no `Symbol.dispose`: it would skip `__enter__` and could not tell `__exit__` about the exception). An async function of JS cannot be cancelled and has no current task behind its first `await`. A plain object is no dict (`json.dumps({a: 1})`) and a `Uint8Array` no `bytes` where code asks `isinstance`. No `in`, negative index or slice on sequences but through `operator`. `a += b` is `a = a + b`, never `__iadd__`. Where neither class answers, an operator gives what JS gives for any object, not a `TypeError` (`timedelta(1) + 1` is a string). Classes take all that `array.map(f)` passes (`array.map(str)`). `structuredClone` and `JSON.stringify` know nothing of most types. |
| `class extends` a class of Python's         | Done, see README. One base; for more, or for keywords of the class statement, extend what `type(name, bases, {})` makes. `super.method()` looks from the base on in the MRO of the instance, so a class that Python puts between the two (`class C(Derived, Mixin)`, both derived from the base) is passed over where `super()` would find it. Static fields are set once the class is made, so a metaclass that goes by the namespace does not see them: the members of an `Enum` cannot be written so. `static set x(v)` does nothing: to assign to an attribute of a class replaces it. What is assigned to `Derived.prototype` after the definition is seen; what is defined on the object that `super` looks from (`[[HomeObject]]`) cannot be reached any more. `toString()` in such a class is an attribute like any other: `String(x)` is `__str__`. `__module__` is `js`. |
| Whole floats in containers                 | `json.loads("[1.0]")[0]` is an object to JS (`typeof`, `===`, `includes`, `Number.isInteger` and use as an index all differ from a number), and so is a NaN made by Python. Returned directly, both are numbers, and a whole float goes back to Python as an int. `-0` from JS is a float: `range(-0)` is a `TypeError`. |
| Output of two languages                   | `console.*` first writes what `print()` has left in the buffers of `sys.stdout` and `sys.stderr`, so the order is kept when they are pipes or files. `process.stdout.write()` and `Bun.write(Bun.stdout, ...)` do not. |
| Iterators of JS                           | `for` and `async for` in Python take items from a JS iterator as they go. Leaving the loop early does not call the iterator's `return()`. |
| `OrderedDict` behind its back             | `collections.OrderedDict` is native and has no list beside the dict: its order is the order of the dict's entries, which can be taken from and added to at both ends. `dict.__delitem__(od, key)`, `dict.pop(od, key)` and `dict.popitem(od)`, after which CPython's raises `KeyError` from `repr` and iteration, do here what the methods of `od` do. |
| Keyword names that are not str            | `f(**{key: 1})` with a key that is not a str is a `TypeError` ("keywords must be strings") whatever `f` is: the names of keyword arguments are passed as strs. CPython hands the dict as it is to what is written in C and takes a dict, so `ast.Name("x", **{key: "y"})` gets to compare the key with its field names and says something else. |
| Sizes                                     | `__basicsize__`, `__itemsize__`, `int.__sizeof__`, `str.__sizeof__` and `type.__sizeof__` give CPython's numbers, because programs add them up and tests compare them with one another. They say nothing about the memory used here. `__flags__` has the bits that mean something here; not `Py_TPFLAGS_INLINE_VALUES`. |
| Too many open files                       | A system call that fails with `EMFILE` collects, finalizes and tries again (`open`, `os.open`, `socket`, `accept`, `socketpair`, `pipe`, `dup`, `opendir`). Other limits that dropped objects hold on to (memory maps, locks on files, child processes) are not treated so. |
| Exception scope verification              | `BUN_JSC_validateExceptionChecks=1` (Bun's ASAN CI sets it) fails as soon as the runtime starts. The C++ of the runtime has to be gone through.                            |
| Signals                                   | Handlers run at safe points (`VMTraps::NeedPythonCalls`), where a system call is interrupted, and between turns of the host's event loop. Not while JS code runs. `SIGPWR` is the engine's. The handlers that the host has for faults (`SIGSEGV`, `SIGBUS`, `SIGILL`, `SIGFPE`, `SIGABRT`, `SIGTRAP`, `SIGSYS`: they report the crash, and the process dies of the signal) are `SIG_DFL` to Python, and setting `SIG_DFL` puts them back. No Windows. |
| Tracing and profiling                     | Done: see README, "Tracing". `sys.monitoring`, `sys.settrace`, `sys.setprofile`, `pdb`, `bdb`, `trace`, `profile`, `cProfile`. Not as in CPython: the numbers and offsets of `INSTRUCTION` events (they are JSC's instructions: `x = 2` is one, so `stepi` in pdb goes further), and offsets in general; `async for` is no `BRANCH`; what depends on an object dying at once (a generator that is dropped is closed, and so traced, when the collector finds it); `remote_exec` and `pdb -p`; no C API (`PyMonitoring_*`, `PyEval_SetTrace`). Cost: none while off or after `DISABLE`. An event costs 1.5 (a `LINE` callback) to 2.7 times (a trace function) what it costs in CPython. Switching a tool on or off writes a byte for each function that is loaded: 8 µs with 40 modules of the standard library imported, against 5 µs in CPython, where it does not depend on how much is loaded. A mark takes 16 bytes, in memory and in a `.pyc` (a sixth of the file): varints would do. |
| `_remote_debugging`                       | The module of a platform where the memory of another process cannot be read: its records and constants, `get_child_pids()`, and a `RemoteUnwinder` that raises `RuntimeError`. So `python3 -m asyncio` is there, and `python3 -m asyncio ps`, `pstree` and `python3 -m profiling.sampling` say that they cannot. No `BinaryReader`, `BinaryWriter`, `GCMonitor`, `get_gc_stats()`. |
| `tracemalloc`                             | Measures no memory: the allocators are the engine's, and most objects are made by a few instructions inline, where there is no place for a hook. `get_traced_memory()` is `(0, 0)` and a snapshot is empty. What it knows, while it is on, is where the objects were made that have a finalizer (files, sockets, instances of classes with `__del__`): `get_object_traceback()`, and so the "Object allocated at" of a `ResourceWarning`. |
| `faulthandler`                            | `enable()` takes the place of the host's handlers of `SIGSEGV`, `SIGFPE`, `SIGABRT`, `SIGBUS`, `SIGILL`: the Python stacks of all threads are written and the process dies of the signal, without Bun's crash report. A fault in code the engine generated goes to the engine first (WebAssembly's bounds checks). No C stack, no list of extension modules, no `_stack_overflow`. |
| Audit events                              | `sys.audit`, `sys.addaudithook`, and the events of what is implemented in C++ (`open`, `os.*`, `socket.*`, `import`, `compile`, `exec`, `sys.*`, `gc.*`, `marshal.*`, `pickle.find_class`, `sqlite3.connect`, ...). Missing: `cpython.run_*`, `code.__new__`, `function.__new__`, `object.__getattr__` of frames and generators, `sqlite3.enable_load_extension` and `load_extension`, `ctypes.*`. There are no hooks for the host (`PySys_AddAuditHook`). |
| `datetime`                                | `_datetime` is native (`runtime/PyDateTime*.cpp`). No `datetime_CAPI` (there is no C API). A date, time or datetime is one 64-bit word, so an object made from a forged pickle keeps only the low bits of a field that is out of range (a day 53 is a day 21; CPython keeps it). `zoneinfo` runs in Python (no `_zoneinfo`): its `repr()` says `ZoneInfo(...)` where the accelerator says `zoneinfo.ZoneInfo(...)`. |
| Codecs for Chinese, Japanese, Korean      | Done, see README. The `__map_*` capsules of `_codecs_*` are there and have nothing in them. |
| `unicodedata`                             | ICU's data, brought up to the Unicode version of this Python by tables (`tools/make_unicodedata_overlay.py`) of what Bun's ICU, which is older, does not know. An ICU that is *newer* than Python's Unicode would show through. Identifiers are normalized (NFKC) by ICU alone. |
| A native module imported again            | One that is taken out of `sys.modules` and imported again is a new module object with a new namespace (README, Imports), but the functions and types in it are those of the first: they are made once. Most of CPython's modules make them anew. `sys` and `builtins` stay the same objects. |
| Frames                                    | `f_lineno` of a frame that has ended by falling off the end of the function, if nothing traced it, is the line of what ran last, as in CPython, except where the ways meet before the end: after an `if` that ends an exception handler, or a conditional expression over several lines, it is the last of those lines in the text, and after `try`/`except*` it is `None`. `f_lineno` is `None` in code the compiler added, also where CPython shows the line an exception was raised on (a frame left through the end of a `finally`: `list` in pdb's post mortem fails on it). |
| Strings                                   | A str is UTF-16 inside, indexed by code point. What is known about a text that is not Latin-1 (how many surrogate pairs, and where every 64th character is) is remembered for the 16 texts last used, until the next collection; a program that works on more long texts than that by turns scans them again and again. A surrogate pair written as two escapes is one character. Hashes are 24 bits wide in places. |
| `bun build` of Python                     | To the bundler a `.py` file is what it always was, an asset (the `file` loader); `with { type: "python" }` is refused. No `--compile` of a Python program.                  |
| When a `.py` module imported by JS runs   | When the module loader fetches it, not when ES evaluation reaches it, because its exports are only known once it has run (Bun's CommonJS modules imported by ES modules are the precedent). So it runs before JS modules imported earlier in the same file, and even if the graph then fails to link. The names a module binds at the top level are known from its symbol table: with those as the export names the body could run at the right time. |
| AOT-compiled JS (`--aot`)                 | Do not mix. A compiled program cannot import a `.py` file, but `bun:python` and `python:` hand it Python objects, which to its types are `anyObject`. Its generic operators call the same slow paths as everything else and give Python's answers. Wrong are: `==` on two operands that are both objects, which compares bits (`AOTComparisonForms.cpp`) and is taken to run no code (`AOTEffectsOfOperators.cpp`); the result of an arithmetic operator, taken to be a number, BigInt or string and kept unboxed (`operationAOT...AsNumber`). To be right, an operand with `anyObject` has to mean the generic form of `==`, unknown code, and a result that is anything. There is no exit from compiled code, so that is paid by every program in which an unknown object reaches an operator. |
| Call sites in Python code with many callees | Only monomorphic inline caches; a second callee takes the slow path each time.                                                                                          |
| Command line (`python3`)                  | Done, see README. Accepted without effect: `-b` (no `BytesWarning` is ever issued), `-d`, `-R` and `PYTHONHASHSEED` (hashes do not depend on a seed), `-X gil`, `-X perf`, `-X presite`, `-X showrefcount`, `-X utf8=0` (the flag only: everything is UTF-8, no locale is consulted), `PYTHONMALLOC`, `PYTHONCOERCECLOCALE`. `-v` prints what `importlib` prints. `sys.argv[0]` of `bun main.py` is the resolved path, not what was typed. No `sys.path` entry for `python315.zip` or `lib-dynload`. `encodings` and `codecs` are imported when a codec is first looked up, not at the start. |
| Interactive interpreter                   | No `readline` module: without `_pyrepl` (`PYTHON_BASIC_REPL`, no terminal) there is no line editing and no history. Tasks that a statement leaves behind run only while a later statement awaits. `bun` without arguments is not a Python prompt. |
| `python3` link                            | `sys.executable` of `bun main.py` is a symbolic link in `/tmp/bun-python-<uid>-<hash of the path of Bun>`, made on demand. It is not on `PATH` (a child that runs `python3` by name gets the system's). A virtual environment made by a program that runs as `bun main.py` links to it, so it dies with the temporary directory; one made by a `python3` that is a link to Bun links to that link (`sys._base_executable`). None of it on Windows. |
| CPython's test suite                      | See README, "Testing". Not run at all: the C API (`test_capi`, `test_cext`, `test_cppext`, `test_ctypes`, `test_embed`), Tk, tools of CPython's repository, Windows, Android, iOS. Skipped by themselves for want of `_testcapi`, `_testinternalcapi`, `_interpreters`, `fork`. Where a whole file is lost because it imports such a helper at the top and few of its tests use it, the suite puts a stand-in written in Python on the path, for that file only (Bun's `test/js/bun/python/cpython-suite/shims`): what needs the helper is still skipped. That is how `test_import`, `test_importlib`, `test_runpy`, `test_pkgutil`, `test_compileall`, `test_bytes`, `test_class`, `test_with` and `test_traceback` run. |
| Windows                                   | `posix`, `time`, `_io`, threads and Bun's `BunPython.cpp` are written for POSIX and do not compile there: until that is done, or Python is compiled out on Windows, the branch breaks the Windows build. |
| Docstrings                                | Native functions, methods, descriptors and types have CPython's docstrings, looked up by name in a table made from CPython (`tools/make_docstrings.py`, `runtime/PyDocstrings.inc`). Modules written in C++ still have whatever their own code gives them. |
| Accidents of CPython's C code in the built-in types | A grid of borderline calls (`extra/grid` in the differential tests) gives what CPython gives, but for these. A `StopIteration` that an iterator written in Python raises with arguments, or a generator's return value, does not pass through `map`, `filter`, `zip` and the like: `next(filter(f, it))` raises a new one. There is one type for built-in functions and methods, no `builtin_method`, so `copy.deepcopy` takes every bound built-in method for atomic. Generators, coroutines, frames and code objects have no `__sizeof__` of their own, and generators and coroutines no `__del__`. `int.__new__(int, 1, 2, 3)`, `str.__new__(str, 1, 2, 3, 4)` and `type.__call__(int, 1, 2, 3)` word the TypeError as `int(1, 2, 3)` does (CPython has two ways in, with two wordings). Two things its compiler and interpreter do show the same way: `'%s' % (x,)`, with the format and the tuple written in place, is compiled there as `f'{x!s}'`, so that a `__str__` that returns an instance of a class derived from str gives a plain str (here the instance, as for `'%s' % x`); and once a `*` in the code has been specialized for a str, bytes or tuple and an int, a count that does not fit is "Python int too large to convert to C ssize_t" there, not "cannot fit 'int' into an index-sized integer". |

# Deferred, undecided, and different on purpose

The list the project keeps of what Python in JSC does not do. Three kinds of entry: **different** (follows from the design, and
stays), **experiment** (needs trying out before it can be decided), **deferred** (known work, not started or not finished).

## Different: follows from the design

| What                                         | Why, and what happens instead                                                                                                                                                                                                    |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Objects are not freed at the last `del`      | There are no reference counts. Finalizers and weak reference callbacks run at the first safe point after the collection that finds the object dead; `gc.collect()` forces it; a thread that has waited for 50 ms (a lock, `sleep`, `select`, a read from a pipe or socket, `waitpid`) collects and finalizes what reference counts would have freed, in that thread, whatever locks it holds; everything left is finalized at exit. See README. (`test_weakset.test_weak_destroy_while_iterating` counts on an element being freed when a generator ends, and fails in the runs in which the set, whose order depends on the hash key, gives that element first: one in three.) |
| What a callback of a weak reference will let go | Counts as the program's data until the callback has run, and it is: the entries of `weakref.finalize`'s registry, of a `WeakValueDictionary`, of a `WeakSet` are reachable until the collection that finds the referents dead has queued the callbacks and those have taken them out. There are the more of them the longer the cycle was, and the heap lets the next cycle grow with them (README, "What waits for a finalizer does not make the heap grow", whose rule cannot help: no collector knows what a callback will drop). Where they are more than half of all that is allocated the heap grows without bound: `while True: weakref.finalize(C(), f)` has 400 MB after 4 million objects, and rising (CPython: flat). JS has the same with a `FinalizationRegistry` whose held values outweigh the rest, in JSC and in V8: 8 million targets with an array of 32 held for each, 1,000 to a turn of the event loop: 1.0 to 2.0 GB in Bun with or without this branch, 2.7 GB in Node 24. To try: a collection when so many weak references with callbacks have been made since the last one, in proportion to those that are alive. |
| What only a temporary holds                  | Finalized at once for memoryviews (`bytes(memoryview(b)[:n])`, `.tobytes()`, `.hex()`, `.tolist()`, `.cast()`, `.toreadonly()`, subscripts, stores in a bytearray), for what `open()` returns if a method is called on it straight away that keeps nothing of it (all that read, write, move or ask: not `detach`, `reconfigure`, `__next__`, `__enter__`) and for a generator that a `for` loop or a comprehension goes through straight from the call, that `in` searches or an assignment takes apart, or that is made as an argument of a built-in function or type that goes through it (`next`, `any`, `sum`, `sorted`, `list`, `''.join` and the like), with any number of built-in iterators around it (`enumerate`, `zip`, `map`, `filter`, `iter`, most of `itertools`: the lists are in README). Not yet: a file as an argument (`json.load(open(p))`), at the head of a loop (`for line in open(p)`) or from anything but `open()` itself (`Path(p).open().read()`, `os.fdopen(fd).read()`, a function of the program that returns one), a file whose use never came because an argument raised, whose method is called with `*` or `**` (`open(p).read(*a)`) or with more or fewer arguments than it takes, of which an attribute is read (`open(p).name`), sockets, generators as arguments of anything else (a function written in Python, `set.update`, `dict.update`, `itertools.tee`, `groupby`, `product`, `f(*g())`, `[*g()]`), passed by keyword, the fifth of five that wait for their use at the same time, one whose use comes after a `yield` in another argument (`next(g(), (yield))`: no use is marked where the frame may be left in between), one in an iterator that has been in a variable (`it = islice(g(), 2); list(it)`), `async for`, a view whose one use is some other native (`len`, `==`, `struct.unpack_from`, `hashlib`, `os.write`, `socket.send`, `b''.join`), a view whose use never came because an exception did, a loop left by assigning to `f_lineno`. Those wait for the collector. |
| Buffered output reaches files earlier        | `open(path, "w").write(text)` counts on the file being closed when it is dropped. Here the streams over files that hold output are kept in a list, and are written out before the program, or anything it starts, can look at a file or do to a file or a descriptor what would come out differently afterwards: `open`, the `stat` family and `DirEntry.stat`, reading, writing, seeking, truncating and closing through `os` or a `FileIO`, `dup2`, `utime`, `rename`, `link`, starting a process, `gc.collect()`, a call of the host. So `f.write("abc"); os.stat(path).st_size` is 3, not 0. Only streams that are exactly what `open()` makes (`TextIOWrapper`, `BufferedWriter`, `BufferedRandom` over a `FileIO`, none of a derived class, whose `write` and `flush` would be seen to run), and not `sys.stdout` and `sys.stderr`. What tells another process by other means that a file is ready (a socket, a signal) does not write them out. The descriptor itself stays open until a collection finds the file: the reader of a pipe whose writer was dropped gets the data, but no end of file until then. |
| `obj[key]` and `obj.name` hold their operands while `__getitem__` or the getter of a property runs | So do CPython's instructions the first time they are executed. Once they are specialized, which they are for a function whose parameters are just those and can be passed by position, they hand them over: if the function deletes its parameters and nothing else refers to the object, it is freed while the function runs. And an `AttributeError` out of the getter that does not say which attribute it was is no longer told (`name`, `obj`). Here an instruction does the same thing each time. |
| `o.m(f())` where the class has a `__getattr__` and `m` is a method of a built-in type | The method is bound before `f()` is called: one that does not apply (`m = str.upper`) raises its `TypeError` there, and one that applies calls itself `C.m()` in what it says of wrong arguments. So does CPython's instruction the first time it is executed, and wherever objects of several classes come by. Once it is specialized it does not bind: `f()` is called first, and the method calls itself `object.m()`. Here an instruction does the same thing each time. |
| A key that is no str in the dict of a class | `type('C', (), {key: 1})`: the key is asked whether it equals a name that is looked up, if their hashes are the same. When, and how often, is not as in CPython: the special methods are looked up by name when they are first needed, not when the class is made; what was found is remembered per class; and an instruction that reads or sets an attribute starts the lookup again if such an `__eq__` has run, so that it goes by what the class, and the class of the object, are afterwards, where CPython goes on with what its walk had come upon. |
| A class that is still being made | While the `mro()` of a metaclass runs, nothing can be looked up in the class. `cls()` and `X.__new__(cls)` are refused as in CPython ("cannot create 'C' instances"), and so is every `obj.__class__ = cls` ("object layout differs"), which CPython lets through where the layouts are the same (both have the same `__slots__`). There the class has no layout of its own yet: `cls.__dictoffset__` and `cls.__weakrefoffset__` are 0, `__doc__` is not in `cls.__dict__`, and `cls.__bases__ = (Other,)` is refused ("'Other' object layout differs from 'Base'", also for `(Base,)` itself) unless it is `(object,)`, which leaves a class whose instances have no `__dict__`. Here the layout is there, and `__bases__` takes what it would take afterwards. |
| A class whose `mro()` leaves out a base | A metaclass can give `class X(int)` the MRO `[X, A, object]`. CPython then has two answers to what `X` is: what is looked up goes by the MRO, and what a type inherits in C (`tp_new`, the number and sequence slots, the layout) came from `int`, the `__base__`. Here who makes the instances goes by `__base__` too, and methods have one answer, the MRO. What takes an object by the kind of its memory still sees the int, float or bytes that it is: `bytes(x)` is `b''`, `complex(x)` `0j` and `json.dumps(x)` `0.0` where CPython refuses `x`, and `float(x)`, `complex(x)` and `int(x)` refuse it in other words. With `object` first in the MRO CPython puts `__hash__ = None` in the class (and hashes the instances all the same); with `__slots__` and no `object` at the end it gives the class a `__dictoffset__`. Of 1,040 such classes that were tried, with some forty questions put to each, 322 answers differed while `__new__` went by the MRO as well. Some of the classes with `__slots__` end CPython with a segmentation fault. |
| `sys.getrefcount`                            | There are no counts: it returns a constant. |
| `gc.collect()`'s result                      | Real: how many objects it found that reference counts would not have freed (README). Not always CPython's number: the first call also finds what has piled up since the program started; what a collection of the engine's own has taken is not counted, one that was pending at the call included; a class counts for as many objects as it is made of here; an object with a finalizer that hangs off a cycle without being in one is not counted; what is written in Python here and in C there (`functools.lru_cache`) has cycles of its own; what has a finalizer is counted when it is freed, which for `gc.collect(0)` and `(1)` is in a later full collection; beyond four million dead cells nothing is counted. `uncollectable` is always 0, `candidates` counts cells. |
| `gc.DEBUG_SAVEALL`                           | Only what `gc.collect()` itself finds goes to `gc.garbage`. Cycles that a collection of the engine's own has freed before are not saved, where CPython's automatic collections save too; one that is pending when `gc.collect()` is called is finished first, and nobody looks on. So a leak detector (`set_debug(DEBUG_SAVEALL)`, the code under test, `collect()`, a look at `gc.garbage`) may see fewer cycles than in CPython, never more. To save them, a collection of the engine's own would have to look at all that has died while the flag is set, as one that is asked for does (time for every dead cell), and keep what reference counts would not have freed in a queue like that of the finalizers, from which the next safe point moves it to the list. |
| A class derived from a sequence that has lost its `__add__` | `class K(tuple)` with an `__add__`, `__radd__`, `__mul__` or `__rmul__` of its own takes part in the operator as a number does, here as in CPython. After `del K.__add__` CPython's table stays as it was: `K() + R()` raises what `tuple.__add__` raises, and `R.__radd__` is not asked. Here what counts is what the class has now. |
| `gc.disable()`, thresholds, generations, `freeze()` | The engine collects when it sees fit, by the bytes allocated, not by the number of objects (an allocation count like CPython's 2000 would cost 35 to 80 us for every 50 us of allocating). `disable()` only stops `gc.callbacks` and `get_stats()` from being told of the engine's own collections: finalizers of cyclic garbage may still run. There are two generations: `gc.collect(0)` and `gc.collect(1)` both collect the young one (what has been allocated since the last collection, the engine's own included), so garbage that has come through exactly one collection, which CPython's `collect(1)` finds, waits for `collect(2)` or the engine's next full collection; and so do the weak references to, and the memory of, what a young collection has finalized. `set_threshold()` is remembered, `get_count()` is `(0, 0, 0)`, `get_objects(generation=0 or 1)` is empty and `2` has everything, `freeze()` does nothing and `get_freeze_count()` is 0. |
| `gc.callbacks` for the engine's own collections | Called after the fact, at the next safe point: "start", what the collection found, "stop". `collected` is 0: only a collection that was asked for counts. A collection that comes between "start" and "stop" goes untold, `gc.collect()` in another thread included, which in CPython does nothing and returns 0 meanwhile. `gc.collect()` in a callback does nothing, as in CPython; in a finalizer that is called in between it returns 0 and the collection is made when the calls that are owed have been made, where CPython collects at once. |
| What `gc` does not hand out                  | The namespace of a class (`gc.get_referents(cls)` gives what is in it), the `__dict__` of an instance that has not asked for it, and whatever is a part of another object here. `get_referents()` leaves out attributes that are numbers. `get_objects()` and `get_referrers()` each cost a full collection that is listened to; cyclic garbage without finalizers, which CPython still has until it collects, is freed by that. They pass over an exception that another thread is raising at that moment and that no code of the program has seen, the entries of its traceback and the frame objects of those, all of which CPython gives. (What a thread is handling is given, here as there. What it has caught and left behind, and is still in the heap here, is gone in CPython.) From a finalizer: the objects that wait behind it in the queue, with all below them, some of which CPython may not have come to yet (the items of a list are dropped last first). An object whose finalizer is going to bring it back, with all below it, until the finalizer has been called; one that waits for its finalizer and that a weak reference has given back to the program meanwhile. The view that `from_buffer()` of `ctypes` makes, while its audit hooks run, and the result of `m[a:b]`, while the `__index__()` of a bound runs, both of which CPython gives. The memoryview that stands for a `Py_buffer` (in a `PickleBuffer`, the iterator of `struct.iter_unpack()`, a scanner of `re`): `get_referents()` of the holder gives the object whose memory it is, as CPython does for the first two (of a view of a view it gives the view, and its scanner says nothing), but `get_referrers()` of that object gives a `managedbuffer`, to which nothing refers, where CPython gives the holder. |
| What `gc` hands out that CPython has not     | What has been finalized and not been freed yet. What only a callback that is owed will let go of (the arguments of a `weakref.finalize()` whose object has been dropped). `for x in y`, where `y` is a list or a tuple, makes an iterator here. CPython 3.15 makes none: it keeps `y` and an index on the stack of the frame. Only `gc` can tell: `get_referrers(y)`, `get_objects()`, and `get_referents()` of a generator that is suspended in the loop. To do the same takes a register for the index in `op_py_get_iter` and `op_py_for_iter`, and whoever reads the iterator's register (the unwinder, `f_lineno = n`, tracing) has to know; it would save about 40 instructions and a cell of 80 bytes per loop. |
| Finalizers and callbacks show up where they run | `sys.settrace`, `sys.setprofile`, `sys.monitoring`, `pdb` and `cProfile` see the code of a `__del__` or of the callback of a weak reference like any other code, as in CPython, but at the safe point after the collection, not where the object was dropped: a debugger that steps may find itself in `importlib._bootstrap`'s `cb`. A signal that comes while one runs is handled in its frame, as in CPython. A warning of theirs that looks beyond their own frames (the `ResourceWarning` about an unclosed file, `stacklevel=2` in a `__del__`) names `<sys>`, line 0, not the line where the object was dropped; in a `gc.collect()`, the line of that call, as in CPython. |
| A finalizer made by another thread than the one that dropped the object | `gc.collect()`, and the main thread as it ends, make the calls that other threads owe and have not begun. A finalizer that never returns then holds the caller, where in CPython it holds the thread that dropped the object: a daemon thread has dropped such an object and waits; the main thread ends, begins that finalizer, and the process never exits. So does one that waits for what the finalizer of another thread's object does, if the caller has taken that other call (the caller's own collection found the object; at exit also: it was owed when the main thread came to its end, or before a further collection of its own): the other thread is not told, and leaves it to the caller. With one exception: if it waits for a lock, an event, a condition or a thread, without a deadline, and every other thread of Python's waits like that too, nothing can move any more, and the caller gives back what it has not begun: the threads that owe are told, and those calls are theirs again. One thread anywhere in the program that polls, sleeps, computes or sits in `accept()`, `select()` or `recv()`, and that does not happen; nor if the finalizer waits with a deadline, for a descriptor, polls with `time.sleep()`, or spins. Nor does it help if the other call lies in the caller's own queue: the caller made that object itself, or its maker has ended and the main thread is the heir, or the caller has left `gc.collect()` early (the handler of a signal raised) and makes the rest at its next safe point. (The two calls are never in one hand, unless the one object holds the other, or both are cyclic garbage that one collection has given to one thread, or that the caller's own collection has found, be it two cycles that have nothing to do with each other: a thread has made and dropped both, the finalizer of the older waits for that of the younger, a collection of the engine's own hands them out, the thread begins: it is stuck, whoever calls `gc.collect()`. CPython's collector calls all the finalizers that it finds in one thread, one after the other, and hangs there too.) Nobody waits for a call that another thread has begun, nor makes the rest of a group that is in that thread's hand: if a thread has begun a chain of 200 objects when `gc.collect()` is called, or when the main thread ends, `gc.collect()` returns, and the callbacks of `atexit` are called, with most of the 200 not finalized; at exit the main thread makes the rest behind those callbacks, but for the call that the thread was in the middle of, which is cut off when the process ends, as any is that a daemon is in. So with the last of what has been given back at a standstill, which the caller and the makers share call by call: at exit it is a maker's, and not over at those callbacks, in every second run. |
| The order of the callbacks of weak references, and of what a call drops | With reference counts a callback is called when the object is dropped, the references to it latest first, and what a call drops is finalized then and there. Here the calls that a thread owes are made callbacks first, the one whose reference was made latest first, then finalizers as they were found. So the callbacks for one object are parted if a reference to another was made in between (`a1 b1 a2 b2`, both dropped: `b2 a2 b1 a1` for `a2 a1 b2 b1`); the callback of a reference to cyclic garbage comes before that of an earlier reference to what reference counts would have freed long before the collector came, and if the one waits for the other, never; what a callback drops, found by a collection inside it, comes next only if the reference to it is later than all that wait (or is another thread's, and the caller is `gc.collect()`); what a finalizer drops comes behind the finalizers that wait (with the same exception). |
| `process.exit()` in a finalizer | The host exits from within a finalizer, or the callback of a weak reference (JS that it has called calls `process.exit()`): within such a call no other is made, and that call never returns: so nothing more is finalized: not what is still queued, not what the program still holds. The callbacks of `atexit` are called. |
| A weak reference that dies with its referent | Its callback is not called. In CPython it is, if the referent's count falls to zero first: `self.ref = weakref.ref(self, callback)` without a cycle. |
| What an entry into the interpreter leaves unwritten | What is written in C++ and runs code of the program enters the interpreter anew: `next`, `list`, `send`, `a, = g()`, `in`, a `key` function. The frame of the entry has words that it does not write (README, "What JSC's own entry leaves unwritten"), and what an earlier call has left there is a reference to the collector for as long as the entry lasts. Seen: in `a, = g(A(), A())` the second `A` is alive while the generator runs, though that has let go of it. It is gone when the statement is over. Which object, and in which statement, goes by how the stack happens to be laid out. JS has the same. |
| What a thread without the GIL has below where it gave it up | The frames of the wait (`Threads::dropGIL`, `takeGIL`, `ParkingLot`, the C library) have words that nobody writes, and the collector also reads the 128 bytes below the stack pointer. What the thread's last calls left there counts as a reference until the thread runs again. Seen on a loaded machine: an entry of the traceback of an exception that `hasattr()` had swallowed, without an edge or a root in a heap snapshot, its address 64 bytes below the stack pointer of a thread that had lost the processor on its way into the wait, in 33 looks of 240; milliseconds later it was gone (README, "An exception that has been caught is gone", what is left). The same above where it gave it up, in the frame of the function that waits, in two ways: a hole in space, which the compiler leaves between two locals and nobody ever writes; and a hole in time: a local that is written only when the GIL has been let go of. A wait of more than 50 ms begins again on a wiped stack; a thread that waits for less keeps alive what its last calls have left there. Seen: `gc.get_objects(); time.sleep(0.0004)` in the callback of a weak reference. The destructor of the buffer in `gcGetObjects()` pushes two registers that both hold the list, which holds every object. What another thread dropped meanwhile was not found by its own collection, and was found by the next one. Where the two words come to lie in the frame of `timeSleep()` hangs on the size of the frame of the function of Python that makes both calls. In one program: one of them 184 bytes below the frame pointer, between `allow` and `until`: in every run, whatever the load (50 of 50, 20 of 20); with that word set to 0 by a debugger what had been dropped was found at once, in 9 runs of 9. With one local less in that function: both in `until`, which is written behind `AllowThreads::release()`: only if the thread loses the processor in between: 89 runs of 120 at a load of more than 100, 1 of 30 at 45. Nothing is wiped for it. Two ways that have not been tried: what C++ swallows unseen (`hasattr()`) could be emptied where it is swallowed, if the exception were still known to be unseen there; and a thread that has parked could be scanned from where it parked, with the registers it had then, since it touches no cell below that. |
| What a dead thread left on its stack         | The C library keeps the stack of a thread that has ended and gives it to the next thread as it is. The frames of the new thread do not write every slot, so a word of the old one may lie where the collector looks for as long as the new thread lives, and if another object has got the cell it referred to, that object is kept. Seen: a cycle that the main thread drops is not found by `gc.collect()` in a thread that was started after another had ended; it is found when that thread has ended too. The engine zeroes the stack below a thread that runs, not memory that is handed on. |
| Order of finalizers, parents and children    | Level by level, in any collection but those at exit when the modules have gone: all the objects that no other object with a finalizer reaches, then, a collection later, what those referred to. The children of two siblings come after both (`y x y1 x1`); with reference counts each child follows its parent (`y y1 x x1`). To go depth first one would have to know, when a finalizer returns, whether it has brought its object back, which takes a collection. Structures more than three levels deep go depth first, in one round, and so does all that dies when the modules have gone. |
| Order of finalizers: a container that was dropped earlier | A collection finds all that has died since the last one, at once, and lets go of it as reference counts would have: there is no time in that. A container that was dropped before the objects in it still decides their order, if no collection has come in between and what held them then has left no trace: `tmp = [c, a, b]; del tmp`, and later the three are dropped one by one, `a`, `b`, `c`: `b a c` here, `tmp` from its end. So with the list that `gc.get_objects()` returns. |
| Order of finalizers in the engine's own collections | As with reference counts where one object with a finalizer reaches another. Siblings (the items of a dropped list) go in the order they were made, not in CPython's, and a cycle of objects without finalizers above them is not seen: only a collection that was asked for looks at all that died. Objects that were dropped one after the other and are found by the same collection go in the order they were made. |
| Order of finalizers of what a container held | As in CPython for what a list, tuple, dict, set, deque, instance, exception, closure or suspended generator held when it was dropped, in a collection that was asked for. Not: what `list.clear()` and `del l[:]` let go of (here in the order it was made, in CPython from the end), nor `deque.clear()` (from the end of its memory: from the right, unless the deque has been used as a queue or rotated, and then neither; CPython from the left); what has left a container that lives on, or that was dropped later (removed, popped, replaced, cleared out), against whatever else was dropped before the same collection: nobody knows when it left, so all of that goes in the order in which it was made (`del d[1]; del x`: CPython what was in `d`, then `x`; here `x` first if it was made first; `b.clear(); a.clear()`: what `a` held first if that is older); what a second container held that has died as well, such as the pairs that a dict was made from or the operands of `|`: an item goes when the last of its dead holders does, so `OrderedDict((i, A(i)) for i in range(8))`, changed and dropped before a collection has come, goes in the order of the pairs; an `OrderedDict` after `move_to_end()` (as it stands then; CPython in the order of the dict underneath, which `move_to_end()` does not touch); `__slots__` (in the order in which they were set, and mixed with the attributes where there is a `__dict__` too; CPython by name, then the attributes); an instance of a class derived from `list` or `tuple` (items, then attributes; CPython the other way round); a struct sequence such as `time.struct_time` (from the end, as a tuple; CPython from the front); attributes that were set in another order than in the first instance of the class (as set; CPython as in the first); an attribute that was set after another had been deleted (in the place of that one; CPython last). |
| Order of finalizers of cyclic garbage that a collection has seen alive | CPython's collector calls the finalizers of what it finds in the order of its lists: the order in which the objects were made, until a collection sees them alive, which puts behind its holder whatever it comes to before that. Here that is followed at exit, where CPython collects before it lets go of the modules, as far as it holds in every program: what the namespaces lead to only through other objects with finalizers goes behind those, right behind; all else in the order of making. In a program that has made fewer than some 2,000 containers since CPython's last young collection, CPython goes breadth first from the namespaces instead, in every version: `a = T('a', T('a1')); b = T('b')` is `a b a1` there and `a a1 b` here; a list of three goes `2 1 0` there and `0 1 2` here; `d = {'k': T('c')}; z = T('z')` is `z c` there; `f = None; raw = Raw(); f = io.BufferedWriter(raw)` goes by the names there and writes what `f` holds, and by the making here, which loses it. What a suspended generator holds goes at the generator's turn there (it is closed, and lets go), and by its own making here. In a big program CPython has no one order. Where objects with finalizers hold one another, the circle is opened where the names lead into it, and where they lead into it at two places that are equally near, at the younger: `a` and `b` know each other, `P` holds `a`, `Q` holds `b`: `P Q a b` in CPython (by the order of the names, or of making), `P Q b a` here; a tree with links to the parent, one object holds the root and another a leaf: `doc cursor root leaf mid` there, `doc root cursor leaf mid` here; the children of one parent: `p b a` there, `p a b` here. Plain cells that hold one another count as one cell, so that what holds one of them holds what hangs off the others; but two that lead to one another only by way of objects with finalizers stay two: `x = T('x'); y = T('y'); a = [x]; b = [y]; x.r = b; y.r = a; ha = T('ha', a); keep = [T('hb', b)]; del x, y, a, b`: `ha hb x y` there, `ha x hb y` here. A stream of a built-in class that another stream wraps has no finalizer of its own any more (the wrapper closes it), so it counts as a plain cell, which is nearer than an object at the same distance: `app.raw = Raw(); app.b = io.BufferedWriter(app.raw); app.t = io.TextIOWrapper(app.b); app.raw.owner = app.t`: the circle is entered at the writer, the raw file goes before the text, and what the text holds is lost, as in CPython. Where the names lead is not always known: where fewer than two finalizers are code of the program only what the objects with finalizers lead to is looked at, and a circle that a list with a name held is entered at its youngest; so among what JS, or a frame, still holds when all else has gone. (A circle that was dropped before the end goes in the order of making, as in CPython: the collection before the modules go finds it.) And for circles of more than 64 cells there is a bound, for the world is stopped meanwhile: 16,000,000 looks at their cells and the references inside them in all, the smallest first. That is enough for a tangle of 90,000 objects with finalizers each of which knows three others, and for a list, a tree or a ring of 1,500,000. Beyond it neighbouring degrees of nearness count as one, more and more of them, and a circle of more than 2,000,000 cells is not opened at all: its objects go in the order of making. After `gc.disable()` it does not collect before the modules go, and keeps the order of making, children first; here the rule holds all the same. At any other time than the exit it is not followed: of `h = T('holder', T('child')); h.me = h; gc.collect(); del h; gc.collect()` the child goes first here, the holder in CPython (without the first `gc.collect()`, the child in both). |
| The thread a finalizer runs in               | The thread that made the object, not the one that dropped it, at a safe point of its own or woken from its wait (README, "Which thread runs a finalizer"); whoever calls `gc.collect()` runs all that is owed. A child follows its parent to the thread that finalizes that one only if one collection finds both dead: an old child of a young parent that a collection of the young takes is its maker's. A generator, coroutine or async generator is its maker's as well: it ought to be the thread that suspended it last, which in programs that hand generators from thread to thread is another one. A finalizer that takes a plain lock which its maker holds while it waits never gets it. What a thread kept in a `threading.local` is finalized by the main thread after the thread has ended, not by the thread as it ends. A thread that is in a system call which an interrupt would cut short (`write`, `send`, `sendfile`, `recv(MSG_WAITALL)`, `connect`, `sigwait`, a foreign function) makes its calls when that returns, however long it takes. That a socket has `SO_RCVTIMEO` or `SO_SNDTIMEO` is known only if `setsockopt()` of that object set it: on one that inherited it (`accept()`, `dup()`, `fileno=`) a `recv()` that is woken begins the time anew. The signal is `SIGURG` for the threads that Python started: a handler of the program's for it hears of signals that nobody sent, and after `signal.siginterrupt(SIGURG, False)` they are not woken from a system call. For the main thread it is the real-time signal that is kept from the program (see "Signals"). Where there is none (not Linux; the main thread of a worker of the host's) it is `SIGURG` as well, which the host can take too (`process.on('SIGURG')` installs it with `SA_RESTART`). |
| `__del__` given to a class after instances exist | The instances there are then are found and will be finalized. Among them are those that were dropped before and that no collection has found yet: an object dies when a collection finds it.                                  |
| All NaNs are one object                      | A NaN is an immediate value: `float('nan') is float('nan')`, so `x in [x]`-style identity shortcuts see any NaN as the same. The sign and payload of a NaN are not kept.                                                          |
| `id()` of numbers, `is` on numbers and strs  | Numbers are immediates: equal ints and floats are identical. Equal strs need not be.                                                                                                                                             |
| A whole `float` becomes a number in JS       | `2.0` handed to JS is `2`, and comes back as the int `2`. Inside a list JS can see the cell that holds it.                                                                                                                        |
| An int beyond 2^53 is a BigInt in JS         | And a BigInt from JS is an int in Python.                                                                                                                                                                                         |
| `None` is `undefined` in JS                  | And both `undefined` and `null` are `None` in Python. So `JSON.stringify({"a": None})`, given a dict, leaves `a` out, as it does for any property that is `undefined` (in a list it is `null`); `json.dumps` writes `null`. To pass `null`: `js.null`. |
| `bytecode`: `co_code`, `dis`, `.pyc`         | The bytecode is JSC's. `co_code` is made up: bytes that differ for code that differs (libraries compare them to tell functions apart), with CPython's jumps, branches, returns and raises where the code has them, which is what `coverage.py` follows, and ending in `LOAD_GLOBAL`, `LOAD_ATTR`, `LOAD_SUPER_ATTR`, `STORE_*` and `IMPORT_NAME` units for the names the code uses and the modules it imports, which is what `inspect.getclosurevars`, cloudpickle and `modulefinder` look for; `dis` shows that and no more. `co_exceptiontable` has the handlers, with a depth of 0. `co_linetable` is the marshalled code, from which `types.CodeType(...)` and `code.replace()` make code again. `replace()` changes what describes the code (names, file, first line, flags) and, in `co_consts`, a number, a str or a bytes for another of its type and the code of a function for code with as many free variables; anything else that the instructions depend on is a `NotImplementedError`. Code with the code of a function replaced cannot be marshalled. A `.pyc` file, and what `marshal` writes for a code object, is read by the build of Bun that wrote it and by nothing else, and CPython's are not read here. What it writes for other values is read by CPython and the other way round, but is not the same bytes from version 3 on: which objects CPython numbers for reference depends on reference counts. |
| Limits of CPython's compiler                 | `SyntaxError: too many statically nested blocks` is here, for the same programs (`Unit::pushBlock()`). CPython also counts as a block the value of a `return`, unless it is a constant, while a `finally` clause is compiled on its way out. That refuses no program that is not refused anyway, for the clause is compiled once more for an exception, with a block in the same place; but where two statements are each one too many, the error may name the other one. Not here: `RecursionError` for a chain of hundreds of thousands of operators, calls or attributes (`'a' + '*a' * 500000`). Only a program that CPython refuses can tell. |
| Comparisons in JS are true or false          | `a < b` in JS is the truth of what `__lt__` returns.                                                                                                                                                                              |
| JS has no `//`, `@`, `+=` of its own         | `a += b` in JS is `a = a + b` (`__add__`, not `__iadd__`). Floor division and matrix multiplication are method calls.                                                                                                             |
| Names chosen to collide                      | Names of attributes are atoms, and the attributes of most objects are properties: JSC's table of atoms and its property tables go by the hash that a `StringImpl` remembers, 24 bits without a key, so whoever can choose names can choose them to collide. 8,000 such names (6,728 where they have to be identifiers) cost `setattr` 154 ms (CPython 1.7), `f(**d)` 135 to 165 (0.3), `sys.intern` 147 (0.9), `compile()` 160 (27), `eval()` of a dict display 189 (31). `f(**d)` is the one that text from outside gets to most easily (`Model(**json.loads(body))`): every keyword name is made an atom, to be compared with the parameters by address. It need not be: a name that no atom has cannot be a parameter's (`JSString::toExistingAtomString`). `codecs.lookup()` makes an atom of the name as well, which goes when the str does. Dicts, sets and what is made of them (`json`, `pickle`, `urllib.parse`, `csv`, `email`, `tomllib`, `http.cookies`) and `pyexpat` are not affected: README, "By what a dict places a str". JS's own `Map`, `Set`, objects and `JSON.parse` are in the same position as names (108 to 215 ms): that is for JSC to decide. |
| Which keys a dict or a set asks              | A program can tell which `__eq__` and `__hash__` of its keys a container calls, in what order and how often. A set, and a dict that holds or has been asked for anything but strs, has its keys where CPython 3.15 has them, so the calls are the same (README, "Where a dict has its keys"). Five things are not. (1) `collections.OrderedDict`: CPython's finds the place of a key in its own list through a second search of the same table, so `od[k] = v`, `del`, `update()` and `fromkeys()` search twice for each key, `pop()` three times, and `setdefault()` asks the key for its hash twice. Here each searches once: the order is that of the entries. It shows with keys of the program's that have one hash (143 of 1,365 groups of cases). And `move_to_end()` takes the entry out and puts it in again here, which counts as an insertion; there the table is not touched. (2) A dict of nothing but strs that has lost some, asked for an object that has the hash of one of its strs and says that it is not equal: how often that str is asked before the search ends depends on the slots that deletions have left, which are not where CPython has them as long as a dict places its strs by the hash of the `StringImpl` (4 of 23,000 random programs). (3) An `__eq__` that takes keys out of the container that is asking it and puts them back: CPython looks only at the table and at the entry it was at, so it may go on through slots that hold other keys now, miss a key that is there, and store it a second time (`popitem()` twice and both back; `t = s.copy(); s.clear(); s.update(t)` on a small set, whose table is part of the object). Here the search starts again and finds the key (4 of 11,346 groups of such cases). (4) A dict display of 16 items or more: CPython stores the first 17 one by one into a dict that grows as it is filled, and makes a dict of every 17 more, which it merges; here room is made for all at once. How often keys of one hash are asked depends on the size of the table at that moment. (5) A mapping pattern, `case {k: v}`, asks each of its keys for its hash twice, CPython three times. |

| Prompt finalization               | Today: an object with a finalizer that is dropped young is finalized at the next collection of the young generation (some 150,000 small allocations, 4 to 15 ms of allocating), or after 50 ms of waiting for anything; never while the program computes without allocating; and one that has come through a collection only at the next full collection, which does not come while the old generation does not grow. A collection of the young generation costs 31 to 80 us since the helper threads are no longer woken for it (it was 95 to 450), so one per 2000 allocations (CPython's threshold, 50 us of allocating) would still make allocating code 1.6 to 2.6 times slower; one per 50,000 would cost 2.5 to 6 %, three times as often as the engine's own trigger. That is the idiom of most tests that still fail for this reason (`del a; assertNotIn(2, weak_dict)`). (2) a full collection now and then while old objects with finalizers exist (1 % of the time). (3) a timer that asks for a collection of the young generation a few ms after an object with a finalizer is made, for programs that do not allocate. Escape analysis for "freed when the function returns" has little to work with: any method call lets `self` escape. |
| JIT                               | Python runs in the LLInt, with fast paths and inline caches there (README, Code). No Baseline, DFG or FTL. The caches are monomorphic.                                                                                                              |
| Consumers of generators in C++    | `for`, `yield from` and `await` resume a generator without leaving the interpreter (README, Code). `sum`, `list`, `any`, `min`, `"".join`, `next()`, `send()` and the like are C++ and enter the VM anew for each item: about 1.3 times CPython's cost. Left: (1) The dict of an instance is not where CPython has it: there it has the table that the instances of a class share, with 64 slots and the names of the attributes of all of them.
